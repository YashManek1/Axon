# R3-02: inert restore rehearsal v1

Decision owner: Astra. Date: 9 October 2026.
Status: **GO for bounded implementation and offline tests. Runtime conditional GO only after the gates below; no runtime or restore acceptance is recorded here.**

## Decision and evidence

Implement a disposable, quiescent synthetic Mongo/Redis/raw-journal preservation rehearsal after acceptance of the bounded R2-02 slice. This is a harness, not a shipped backup/restore command. It accepts no arbitrary database URI, external backup, customer credential or destination override. No product API, schema, Rust wire format, migration or deployment changes belong to this milestone.

The active packet, `docs/axon-inert-restore-rehearsal-v1.md`, identifies backend startup/recovery and journal opening as mutating operations. `docs/decisions/R2-04-durability-contract.md` permits recovery to enqueue ACCEPTED outbox records and journal startup to turn unfinished entries into UNKNOWN. Consequently, restored data must remain inaccessible to backend, workers and agents. Mongo-only copying cannot establish preservation of Redis fencing or journal evidence.

The current context/tracker and `docs/verification/connected-agent-20261008/runtime-acceptance-r10.md` establish bounded execution acceptance, not installation/restore acceptance. Reuse that evidence without rerunning it. Parent supplied the existing zero-repository graph result; targeted reads were used without rebuilding a graph. Source inspected only at the named harness orchestrator imports and library safety entry points; changing reconciliation/frontend source was not inspected.

## Exact interface and invariants

1. **Closed resource plan.** Generate a cryptographically random run identity and distinct source/destination names. Use only reviewed, already-local Mongo/Redis images pinned to image IDs/digests, identical versions on both sides; record database and dump/restore tool versions. No pull, build, installation, backend, runner service, agent, socket mount, privileged service, execution target or network egress. Prefer `network=none`, no published ports, and bounded `docker exec` database utilities talking to their own container's loopback. If transport requires a private network or published loopback ports, decide and review that concrete topology before runtime. Never use the product Compose stack.
2. **Refuse existing destinations.** Preflight every planned container, volume and private output path for absence; create exclusively and record creation intent before each mutation. An existing empty database/resource is also refused. After fresh destination creation and immediately before import, verify exact ownership/configuration, no application collections, empty Redis keyspaces, and absent journal destination. Mongo system administration created by the owned image/bootstrap must be explicitly distinguished from application data. No drop, flush, prune, overwrite, `--drop`, repair-in-place or adoption of a failed destination. A second attempt receives entirely new identities/resources.
3. **Complete preservation.** Seed at least two synthetic tenants with distinct users, agents, jobs, approvals/previews, terminal success, UNKNOWN plus its exact hold, and pending ACCEPTED intent. Include current optional resolution witness/intent fields after their contract stabilizes, without running resolution. Enumerate every collection and collection option/index in the selected application database, including empty collections and a synthetic sentinel collection unknown to the fixture allowlist. Record and compare BSON types/values, IDs, relationships and collection counts using deterministic typed canonicalization. Preserve index key order and all semantic options, especially target-owner uniqueness, partial filters, sparse/collation/TTL settings; document any excluded server-generated metadata. Refuse unsupported collection/index types rather than omit them.
4. **Three mandatory components.** Mongo archive plus collection/index inventory, Redis persistence snapshot plus logical inventory, and raw synthetic journal files are mandatory parts of one manifest. Redis is a fresh dedicated instance: enumerate all logical databases and preserve all keys, types, binary values and fence/queue identities. Use bounded synthetic values; queue-shaped data is not evidence of a working BullMQ restore. Preserve journal bytes without importing/opening the agent journal module; include unfinished entries to detect accidental recovery. Original UNKNOWN reason, requiresReview, hold owner/fence and ACCEPTED state must be unchanged. No new run/attempt/approval identities or release intents may appear.
5. **Expiry and quiescence.** Stop all fixture writers before inventories/export; only explicitly listed snapshot/read commands remain. No application runtime ever starts. Use non-expiring fixtures plus expiry-sensitive fixtures whose deadlines exceed the entire bounded run with margin. Compare absolute expirations and natural remaining lifetime, with a documented clock/precision tolerance; any unexpected expired record fails. Do not reset TTLs, pause/change clocks, disable index semantics or normalize away missing records. This proves only a quiescent synthetic snapshot, not live cross-store atomicity.
6. **Strict manifest.** Versioned schema with exact component set, run identity, synthetic provenance, release/source fingerprints, image IDs/digests, tool/format versions, capture times, sizes, SHA-256 hashes, collection/index inventories, fixture expectations and private relative paths. Reject unknown schema/format/version, missing/extra components, duplicate identities/paths, invalid tenant references, unexpected files, oversized input and checksum mismatch before destination import. Validate real paths beneath the owned private root and reject absolute paths, traversal, symlinks/reparse points and archive escapes. Hash the manifest in the sanitized evidence record. Checksums establish integrity of this locally generated fixture, not authenticity of arbitrary backups.

## Failure, environment and cleanup contract

Use explicit local Docker context/endpoint and verify daemon identity before mutation and cleanup. Inherit only reviewed CLI prerequisites; never ambient application credentials or Docker endpoint/TLS overrides. Generate child-only synthetic secrets where required. Verify private directory permissions/ACLs on Windows; POSIX mode flags alone are insufficient. Raw dumps, journal contents and secrets stay out of evidence and terminal output.

Every native operation has an enforced timeout (at most 30 seconds by default), finite readiness attempts, capped stdout/stderr and a total run deadline. Timeout, malformed output, spawn/stdin failure, nonzero status or uncertain completion fails the phase. Kill/confirm termination of the owned producer, account for any container-side command still running, then clean up. Never retry an uncertain import or snapshot mutation automatically. No shell command interpolation for fixture data.

Maintain an intent/creation/inspection/cleanup ledger on partial failure. Delete only exact newly owned resources after reinspection of owner/run labels, name and immutable IDs where available; never delete by broad labels alone. Docker volumes lack immutable object IDs: additionally record creation time, driver/options, mount/configuration fingerprint and exact associated container mounts. Changed or unverifiable volume identity fails closed; do not describe a volume name as an immutable ID. Unconfirmed creation needs bounded exact-name reconciliation, not silent ledger omission. Unknown replacement or unprovable ownership means leave the resource untouched and report cleanup incomplete.

Runtime PASS requires comparison success, forbidden-effect assertions and independently verified absence of every owned runtime resource and private raw/secret artifact. Retain only sanitized evidence. Failure to clean up or verify absence is a nonzero failed rehearsal even when data comparison passed; record exact leftovers for authorized follow-up. Do not remove or stop preexisting unrelated resources. The absence claim covers the isolated rehearsal resources and access to its data, not every backend/agent on the user's daemon.

## Reviewed utility reuse

Candidate imports from `scripts/codex/approval-connected-agent-lib.mjs`: nonce generation, redaction, environment construction, native invocation, exact inspection, ownership checks and cleanup. Record hashes and independently review suitability at stabilized inputs. Reuse does not authorize executing the previous orchestrator or importing application startup.

Inspection found new-contract gaps: `assertFreshDatabase` permits existing empty collections; `runNative` has unbounded output buffers and timeout settlement needs producer accounting; temporary-path validation is tied to the old namespace and does not establish Windows ACL privacy; volume identity is its name; cleanup can skip attempted entries without IDs. New restore-specific wrappers/guards must close these gaps. The prior Compose validator, lifecycle report, internal endpoint mode and agent/nested cleanup logic are not approved for this DB-only topology. Preserve accepted helpers unchanged; a shared-helper change needs explicit ownership handoff and affected regression review. These are reuse limitations, not a reopening of r10 acceptance.

## Rejected alternatives and remaining risks

Reject starting the normal backend for verification, opening the journal through Rust, Mongo-only restore, dropping a destination, restoring into shared resources, arbitrary customer backup inputs and automatic resume/retry. Each either changes evidence, omits required persistence or crosses the authorized boundary.

Implementation/runtime evidence and final acceptance remain missing. Local Docker access is powerful, so topology/configuration and cleanup are acceptance gates, not assumptions. Success closes only this inert synthetic preservation slice. Clean installation, real database credentials/roles, live consistency, interrupted/partial cross-store recovery, cross-version migration, dispatch reactivation, customer backup authenticity, actual process-crash recovery, multi-host operation and production readiness remain unproved and separately scoped. R3-02 must remain open.
