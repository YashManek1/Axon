# Axon Technical Audit, Impact Analysis and Release Plan

Reviewed 9 September 2026. Planning and verification only; application defects described here have not been fixed by this investigation.

Implementation follow-up: stabilization round 1 is now in progress. The findings and test results below describe the original audit snapshot; use the [live TODO](AXON-LIVE-TODO.md) and [round 1 acceptance report](axon-stabilization-round-1-2026-09-09.md) for subsequent fixes and current verification. The [execution contract](axon-execution-contract-v2.md) documents the next milestone; it is not implemented yet.

## The decision you can act on

**Axon is a substantial working engineering foundation. It is not yet ready to be sold as reliable unattended production infrastructure.** Continue customer discovery now, repair the execution and access-control paths, then offer a bounded installation for one customer's low-risk procedure. A polished interface belongs in that release, but its status indicators must reflect what actually happened.

This assessment does not mean starting over. Keep the React application, Node control plane, Rust agent, MongoDB and queue infrastructure. Fix their contracts and lifecycle behavior before adding a broad workflow engine. The commercial scope and prices are in the [current-product plan](<C:/My Project/Axon/docs/axon-current-product-plan-2026-09-09.md>); the customer experience is specified in the [UI/UX plan](<C:/My Project/Axon/docs/axon-ui-ux-product-spec-2026-09-09.md>).

There is no defensible percentage such as “85% production-ready.” A single wrong-server execution can invalidate a hundred working features. Progress should be measured by complete customer journeys passing defined release gates.

## What is implemented

| Area | Existing progress | What it does not establish |
|---|---|---|
| Browser application | Authentication, dashboard, agents, jobs, job detail, audit, settings, themes, responsive styles | Fully usable onboarding, truthful aggregate statistics, working workflow editor or tested recovery |
| Control plane | Express routes, MongoDB models, validation, Socket.IO, API keys and short-lived agent tokens | Correct separation of customer admins, platform admins, users and machines everywhere |
| Execution | BullMQ workers, HTTP and shell jobs, signed dispatch, acknowledgment and result handling | Exact target selection, distinct attempt identity, safe retry or correct success classification |
| Rust agent | Connection, command verification, process execution, timeout handling, telemetry, optional sandbox modes | Durable duplicate suppression, bounded output, tested Linux process-tree cancellation or offline workflow autonomy |
| Scheduling and coordination | Repeat jobs, dependency checks, Redis locks and fencing counters | Run-specific workflows, lease renewal or fencing enforced by the external system being changed |
| Evidence | Audit records and chain verification, job history, output summaries, log delivery, metrics/traces | Immutable completion evidence, live process output throughout execution, complete records under concurrency and failures |
| Delivery | Dockerfiles, Compose, CI tests, agent release workflow, Azure backend deployment workflow | A verified install-to-upgrade-to-restore process, compatible release bundles or high availability |

The application's execution path is: browser request → user authorization → job configuration → queue → Node worker → selected agent socket → Rust process → result → history/audit → browser. Automation will insert a durable procedure coordinator before dispatch; it should reuse the rest of this path.

## Fix order and dependency impact

1. **Contain authority and unsupported promises:** T01–T03, T09 and T18. Establish a role/action matrix and remove unsupported arbitrary execution paths from the pilot contract. Define compatibility handling for existing JWTs and agent credentials. Do not expose a public multi-customer signup deployment meanwhile.
2. **Specify one execution contract:** T04–T08. Agree target, action/version, run/attempt/operation IDs, deadline, result schema and retry policy together. These fields affect the database, queue, signature, Rust agent, logs, audit and UI. This is the highest-impact change; implement one end-to-end slice rather than disconnected patches.
3. **Prove the lifecycle under failure:** T10, T13–T16. Add durable transitions, bounded output and honest uncertainty. Test duplicate, delayed and lost messages before enabling automatic retry. An unsafe retry fix can be worse than no retry.
4. **Make the release installable and recoverable:** T19–T22. Build the intended Linux environment and release bundle. Restore from a backup before customer installation. Run this work alongside lifecycle tests once contracts stabilize.
5. **Complete the customer journey:** T17–T18 plus the UX plan's R0 scope. Integrate against real APIs after the execution contract stabilizes; a prototype can be designed earlier. Test onboarding and a failed run with a new user.
6. **Add schedules only when promised:** T12, then T11 for paid automation. An explicitly manual initial package can defer scheduling and workflow features; it cannot defer target, authorization or result correctness.
7. **Optimize based on use:** T23, richer maps, saved views and notification preferences after the first complete path. Accessibility and truthful states belong in the initial path, not this deferred bucket.

Required migration record for each change: old shape, new shape, backfill/default policy, compatibility window, rollback behavior and affected tests. Never infer that all running agents upgrade at the same moment. If a protocol change cannot be made compatible, pause dispatch until the environment's versions are verified.

## A practical deployment product

**First supported shape:** one customer-owned installation; one Node API/worker process with one replica; one MongoDB deployment and one Redis deployment; one same-origin HTTPS entry point; up to five Linux agents for the current-product package. The customer owns the infrastructure account and remains able to stop/revoke the agents. Separate unrelated customers into separate installations initially.

This is a deliberately bounded product, not high availability. Socket routing is process-local; adding a second backend replica without routing/dispatch ownership work is not safe scaling. Do not offer automatic failover or a 99.9% SLA before designing and operating those capabilities.

Use a reviewed standalone manifest rather than asking a buyer to debug development overlays. A reverse proxy terminates TLS and forwards HTTP plus WebSockets. Redis and MongoDB stay private, require appropriate authentication, persist data and have tested backups. Agent connections go outward to the authorized endpoint; do not claim this alone is unique to Axon or that it eliminates security review.

When automation relies on MongoDB transactions/outbox behavior, its supported MongoDB topology must be a replica set or other transaction-supporting deployment. A single-member replica set permits transactions but is not resilient to losing that host. The current Compose MongoDB is not configured as one. [^4]

### Installation and operating sequence

| Stage | Concrete work | Evidence to save |
|---|---|---|
| Preflight | Confirm Linux distribution/architecture, outbound DNS/TLS, proxy policy, time synchronization, storage, ports, least-privilege service account and script dependencies | Sanitized compatibility report; explicit allowed actions and target inventory |
| Package | Pin all image/binary versions, checksums, schema version, protocol compatibility and supported runtime; review dependency vulnerabilities and licenses at release time | Release manifest and immutable artifact identifiers |
| Bootstrap | Generate instance-specific keys; one owner account; enroll with short-lived scoped credential; configure local action allow-list without wildcard shell access | Successful connection and revocation test; no secrets in command history, screenshots or source |
| Verify | Execute synthetic success, nonzero exit, offline target and timeout scenarios through the actual UI/API/agent path | Run URLs and sanitized evidence, including no incorrect target |
| Back up | Back up MongoDB, queue persistence/configuration and necessary encrypted-secret/key material separately with access control | Restore on a clean isolated host; prove configuration and history can be recovered |
| Recover | Reconcile restored pending/running attempts with agent journals/external checks; unknown side effects require review | Restored queue does not automatically replay an unsafe operation |
| Upgrade | Pause new dispatch, reconcile/drain active work, back up, migrate, verify compatible agents, smoke-test, resume | Versioned checklist, operator, before/after results and explicit rollback conditions |
| Roll back | Revert images only if data/protocol compatibility permits; otherwise restore to an isolated environment and reconcile effects | Tested instructions; no blanket promise that application rollback reverses external server changes |
| Operate | External availability monitoring; queue age, failed/unknown run count, stale agents, disk usage, backup freshness and certificate expiry; alert the named responsible person | A real test notification and support contacts; no invented 24/7 commitment |
| Offboard | Pause schedules, complete/reconcile work, export agreed data, revoke credentials, uninstall service and handle retention | Customer confirms removal; shared secrets rotated where relevant |

Provisional pilot recovery objectives: restore service within four staffed hours and recover durable history to the agreed backup point, initially no more than 24 hours old. These are targets to test and negotiate, not an SLA. If the customer's acceptable data loss is less, change backup/recovery design and pricing before accepting the installation. Queue recovery and recovery of external effects require reconciliation even with frequent backups.

For a control-plane outage: ongoing local processes may complete; new work is not assumed to run; unresolved attempts become unknown until evidence reconciles them. For an offline agent: keep a visibly blocked run only until its defined deadline; never move it to another machine. For storage failure: reject new work if its required state/evidence cannot be durably recorded. Document these rules in the interface and handoff.

## Release gates and definition of done

**G0 — demonstration:** isolated synthetic servers/data; limitations visible; no public arbitrary-command endpoint. Show the actual successful and failed path. Prototype footage is explicitly labeled if any interaction is simulated.

**G1 — bounded paid pilot:** T01–T09 resolved or unsupported capabilities disabled at the server boundary; durable identity/evidence and relevant T10/T13–T22 acceptance checks pass; one installation, agreed actions, operator and server scope. Manual-only is acceptable when stated. No known wrong-target, cross-tenant, false-success or unsafe-retry defect may remain.

**G2 — unattended recurring use:** schedule reconciliation, restart/reconnect, lease loss, noisy process, backup restore and upgrade drills pass on supported Linux; product and queue status agree; support ownership and operating limits documented. Run the agreed expected workload plus a modest burst for a defined observation period, report measurements, and avoid extrapolating to untested fleet sizes.

**G3 — automation or production-changing procedures:** run-scoped coordinator, approval/version/target binding, external effect idempotence or safe reconciliation, resource exclusion and relevant failure matrix pass. A tested read-only diagnostic does not qualify a database migration or fleet restart automatically.

Each gate needs a saved report with version, environment, inputs, observed outcomes and unresolved restrictions. Tests relevant to a change should be meaningful: real queue retry behavior, authorization matrices and real agent execution are essential; a test that merely repeats a CSS class is not.

## Effort and the income tradeoff

The earlier current-product allowance was 80–140 focused engineering hours. Reserve another **20–40 hours once** for the initial UX slice, guided setup, run detail and basic server map/list integration described in the UX plan. The revised rough allowance is **100–180 hours** before unknown customer integrations. It is not a fixed-price implementation estimate; security/protocol findings can change it.

At ten engineering hours a week that is roughly 10–18 weeks. Automation adds its own 73–122 hours after this shared foundation, so a bounded automation pilot is roughly 173–302 hours in total. Do not count the foundation or the shared UI twice. Full mature fleet/delegation features are outside these allowances.

This matters commercially: two products are not two independent full-time projects. Spend the sales allocation finding a customer procedure while engineering builds one shared execution path. If income is needed sooner, sell a carefully scoped operations-automation service using suitable existing tools, clearly distinguishing that service from verified Axon adoption. Do not use a revenue target to waive a safety gate.
